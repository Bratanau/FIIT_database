# Лабораторная работа №2. Разработка SQL-запросов и аналитических сценариев для интернет-магазина

## Состав проекта

- `seed.sql` — добавление расширенного и повторно запускаемого набора данных;
- `dml_operations.sql` — демонстрация `INSERT`, изменения статуса заказа, массового `UPDATE`, безопасного `DELETE` и `ROLLBACK`;
- `queries.sql` — шесть запросов с `JOIN` и `GROUP BY`, а также четыре запроса с подзапросами;
- `report.sql` — комплексный аналитический отчёт с CTE и сравнением выручки по месяцам.

`seed.sql` добавляет:

- 36 дополнительных покупателей;
- 45 дополнительных товаров, распределённых между имеющимися категориями;
- 60 заказов с позициями товаров.

- пять состояний заказа: `created`, `paid`, `shipped`, `delivered`, `cancelled`;
- события с января 2025 года по 2026 год;
- повторные заказы от одних покупателей;
- покупателей без заказов и товары без позиций заказа;
- нулевые остатки, NULL в допускающих это полях исходной модели и товары, отмеченные как неактивные.

У некоторых покупателей не будет заказов, для части товаров не будет позиций заказов. Это даёт результаты для `LEFT JOIN`, `EXISTS` и `NOT EXISTS`. Товар с SKU `LAB2-SKU-00045` также не связывается с заказами и используется в демонстрации корректного удаления.

Скрипт формирует тестовые записи через `generate_series`. Конфликты email/SKU пропускаются через `ON CONFLICT`, а существующие заказы и позиции повторно не добавляются. Суммы новых заказов вычисляются из позиций. Вставки выполняются транзакционно.

## 2. Операции DML и транзакция

`dml_operations.sql` выполняет в одной транзакции следующие действия:

1. Создаёт нового покупателя и товар.
2. Создаёт заказ и связанную с ним позицию.
3. Переводит новый заказ из `created` в `paid`.
4. Массово переводит старые заказы со статусом `created` в `cancelled`. Условие ограничивает изменение только заказами до 1 января 2026 года.
5. Удаляет товар `LAB2-SKU-00045` только при отсутствии ссылок на него в `order_items`. Это соблюдает внешний ключ `ON DELETE RESTRICT`.
6. Выполняет `ROLLBACK`, отменяя все перечисленные изменения.

Сообщения `NOTICE` показывают, какие шаги выполнены и сколько строк затронуло массовое изменение. После завершения скрипта исходные данные остаются неизменными.

## 3. Операционные запросы и агрегация

### Многотабличные запросы

1. Подробный состав заказов: покупатель, заказ, товар, количество и сумма позиции. Используются четыре таблицы.
2. Покупатели без заказов. `LEFT JOIN` сохраняет клиентов без совпавших заказов; NULL в ключе заказа выделяет отсутствие связи.
3. Завершённые заказы активных/VIP-покупателей. Условия одновременно проверяют покупателя, состояние заказа, товар и категорию.

Каждый из трёх запросов соединяет не менее трёх таблиц.

### Агрегация

4. Для каждого покупателя рассчитываются число заказов, общая и средняя сумма, даты первого и последнего заказов. `LEFT JOIN` включает покупателей без заказов.
5. Для каждой категории вычисляются проданное количество, сумма продаж, средняя цена и число заказов. `HAVING` оставляет категории, где продано не менее 10 единиц.
6. Заказы группируются по календарным месяцам; выводятся количество, сумма, среднее, минимальное и максимальное значения. Отменённые заказы исключены из продаж.

Запросы используют агрегаты `COUNT`, `SUM`, `AVG`, `MIN` и `MAX`.

## 4. Подзапросы и нетривиальные ситуации

7. **Сравнение со средним по своей группе:** товары дороже средней цены товаров той же категории.
8. **`EXISTS`:** покупатели, у которых есть завершённый заказ хотя бы с одной позицией количеством не менее двух единиц.
9. **`NOT EXISTS`:** активные товары, которые не встречались ни в одной позиции завершённого заказа.
10. **Коррелированный подзапрос:** заказы, сумма которых превышает среднюю сумму заказов конкретного покупателя. Внутренний запрос использует `customer_id` текущего заказа.

## 5. Комплексный отчёт на CTE

1. `eligible_orders` — исходные заказы, кроме отменённых.
2. `order_line_metrics` — для каждой операции рассчитываются количество проданных единиц, сумма по сохранённым ценам позиций и число строк заказа.
3. `order_metrics` — показатели позиций связываются с заказами. `LEFT JOIN` сохраняет заказ, даже если у него пока нет позиций.
4. `monthly_metrics` — заказы агрегируются по месяцу: количество заказов и покупателей, проданные единицы, выручка и средняя выручка на заказ.
5. `month_comparison` — `LAG` добавляет выручку предыдущего месяца.
6. Итоговый `SELECT` показывает абсолютное и процентное изменение выручки. `NULLIF` защищает деление на ноль; для первого месяца предыдущего значения нет, поэтому сравнение возвращается как NULL.

Выручка отчёта рассчитывается по `order_items` (`quantity * unit_price`), то есть по цене, зафиксированной в момент покупки, а не по текущей цене товара.
